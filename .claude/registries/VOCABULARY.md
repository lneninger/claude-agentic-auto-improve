# Business Concept Dictionary

> **Purpose:** one-paragraph definitions of every domain term used in concept contracts. Prevents agents and user from drifting on ambiguous language.
>
> **Rule:** a term enters this file the first time it appears in a concept contract. Ambiguous terms become **open questions** to the user in the contract — never guessed. Once the user confirms the definition, the data-architect appends it here.
>
> **Two tiers:** Universal (cross-project engineering vocabulary) and per-project domain vocabulary, which (registry layout 2) lives in domain files `VOCABULARY/<domain>.md` beside this file, named by the `## Project tier` pointer at its end.

---

## Universal Vocabulary

- **CodeGraph** — the semantic knowledge-graph index of a codebase produced by the `codegraph` CLI. Stored at `<project>/.codegraph/codegraph.db`. The authoritative answer source for "where, who, what" questions about code. Exposed to Claude Code as a set of MCP tools (`mcp__codegraph__*`; the server offers different tools from one release to the next, so no document names one). Established as the primary investigation tool by the CodeGraph-first protocol (`~/.claude/hooks/codegraph-first-guard.py`). NOT a documentation file or a memory store — it is a queryable graph rebuilt from source.
- **Symbol Node** — a vertex in the CodeGraph representing a code symbol (class, interface, method, property, field, function, module). Carries a stable id across runs, a name, a kind, and a source location. Operations: a symbol lookup (find) and a symbol inspection (inspect), asked of CodeGraph through a `mcp__codegraph__*` tool.
- **Code Edge** — an edge in the CodeGraph between two Symbol Nodes representing a call, reference, inheritance, or containment relationship. Drives the callers, callees and impact questions.
- **Investigation Turn** — the span between two `UserPromptSubmit` events. Within one turn, the CodeGraph-first gate opens after the first `mcp__codegraph__*` call (the session's marker `turn.json` is written); the next `UserPromptSubmit` resets the gate by deleting the marker. This is the unit of "fresh investigation budget" enforced by the protocol.
- **Entity** — an object with identity that persists over time. Two entities with the same field values are distinct if their identities differ. Entities own their data and enforce their invariants.
- **Value Object** — an immutable shape defined only by its field values. Two value objects with equal fields are interchangeable. Has no identity. Used for things like Money, DateRange, Coordinates, TrailingStopState.
- **Aggregate** — a cluster of entities and value objects treated as a single consistency boundary for writes. The aggregate root is the only entity an outside caller may reference.
- **Domain Event** — an immutable record of something that happened in the domain. Past tense. Carries payload needed by downstream consumers.
- **Command** — an imperative request to change state. Present tense. May be rejected.
- **Port** — an interface declared by the domain that describes a dependency (e.g. `IMarketDataProvider`).
- **Adapter** — an implementation of a port that bridges to a specific technology (a third-party service client, a backtest data file, etc).
- **Invariant** — a rule that must always be true for an entity or aggregate to be in a valid state.
- **Projection** — a read-optimized shape derived from entities, used for queries and UI.
- **Saga / Process Manager** — a long-running coordination of multiple domain events toward a business outcome.
- **BatchedInQuery** — the approved pattern for EF Core queries that filter by a key set whose size may exceed the database's per-statement parameter limit (SQL Server caps at ~2100). The key set is split into chunks of ≤2000 and executed as one server-side query per chunk, with the results concatenated into a single materialized list. Callers supply a factory that turns a chunk into an `IQueryable<T>` and retain full control over `AsNoTracking()`, projections, and additional filters. Forbidden alternatives: (a) the naive `.Where(e => hugeSet.Contains(e.Key))` which generates an oversized `IN()` and fails with a TDS protocol error, and (b) the `.ToListAsync()` + in-memory filter workaround which defeats pagination and wastes memory on the full table.
- **Startup Task** — a unit of one-time, fire-and-forget work that runs at application startup in its own DI scope. Implemented as a class implementing `IStartupTask` (Domain port) with a `Name` property and a single `ExecuteAsync(IServiceProvider scopedProvider, CancellationToken ct)` method. Registered via `services.AddStartupTask<T>()`. A single `StartupTaskRunnerHostedService` (inheriting `BackgroundService`) executes every registered task once at startup, in registration order, with a fresh scope per task and centralised exception isolation. Replaces the ad-hoc `_ = Task.Run(async () => { ... })` pattern that silently swallows exceptions, captures scoped services against the root provider, and is impossible to test as a unit. Tasks check their own feature flags inside `ExecuteAsync` and early-return if disabled. Failures are logged with the task `Name` and do NOT cancel subsequent tasks. Tasks that MUST complete before the HTTP server accepts requests need a different mechanism (`IHostedLifecycleService.StartingAsync`) — the runner's `BackgroundService` base runs concurrently with the server.
- **Claude data root** — one candidate `.claude` directory in the ordered search space that every Claude path locator walks when looking for Claude *data* (registries, concept contracts, north-stars, the area map, the contract-accuracy ledger, the derived-scan cache). Produced by `claude_roots()` in `.claude/hooks/_project_paths.py`. Each root carries an implicit rank: rank 0 is the `.claude` directory under `$CLAUDE_PROJECT_DIR` (present only when Claude Code launched the process — **unset in a plain shell**), **rank 1 is `SELF_ROOT`** — the `.claude` directory the resolver module itself lives in — rank 2 is the one under `$PWD`, and rank 3 is the one under `$HOME`. Rank 1 exists because ranks 0 and 2 are both caller-controlled and both silently wrong when the caller is a plain shell in a subdirectory; the resolver ships *inside* the tree it searches, so its own location is the one rank a caller cannot get wrong. A root is *selected* by the first-that-**contains-the-sought-thing** rule, not by mere directory existence: `registry()` takes the first candidate for which the file `is_file()`, and `first_populated_dir(roots, pattern)` takes the first directory that actually holds a match for `pattern`. When no root holds it, the rank-0 (preferred, repo-shaped) candidate is returned so that a *writer* creates the file in the right place. Roots are never unioned — unioning would leak one checkout's contracts into another's inventory and into the accuracy ledger. Distinct from a **Claude runtime root** (`logs/`, `state/`), which resolves through `project_dir()` alone and has no `$PWD` fallback, because it holds machine-level runtime rather than repository content.

- **Plugin repository** — a sibling checkout holding the project-independent half of a Claude Code setup, so that a second project can adopt the same workflow without copying files by hand. It is a source to copy from. It is **not**, unless it also carries a plugin manifest and a marketplace entry, something the editor can load by itself: Claude Code's own plugin mechanism is the `enabledPlugins` and `extraKnownMarketplaces` pair in the workstation settings file, and a repository absent from both is a vendoring source rather than a package.
- **Vendored asset** — a file that lives in the plugin repository and is copied, unchanged, into a consuming repository. The consuming copy is committed, so the repository works when the plugin checkout is absent, and the sync tool is what keeps the two equal. Exactly one copy exists in the consuming repository, at its ordinary path — never a second copy in a subdirectory named after its owner.
  - **Correction (2026-10-31, `.claude/concepts/2026-10-12-dedupe-claude-config.md`, block 14):** since that contract, agents and skills are not Vendored assets; they are **Plugin-delivered assets**. Hooks, scripts and their tests stay vendored, because this repository's settings, skills and tests open them by path. An installed **Add-on hook** is also a Vendored asset, of the add-on's file, but its two paths differ: the plugin keeps it in the add-on's folder and the project runs it from its own hooks folder. A file in the sync config's `repo_owned` list is the exception: the repository keeps its own text, and a difference is reported, not copied.
- **Ownership tier** — the label that says whether a given setup file is owned by the plugin, and therefore replaceable on sync, or owned by the consuming project, and therefore never touched. Every setup file carries exactly one tier. The tier is recorded in `.claude/.sync-config.json` and nowhere else; a file that no tree's file list names is a local asset by default.
- **Sync direction** — which way changes may travel for one synced tree. Three values: `bidirectional`, `plugin-to-repo`, `repo-to-plugin`. It is a property of the tree, recorded once in the sync configuration, and never a property of an individual file. Every tree holds `bidirectional` today; the other two remain defined so a future tree can use one.
- **Vendored-asset drift** — the condition where a vendored asset and its plugin original no longer match. Detected by comparing content hashes of the two files **after normalising encoding** — folding line endings and stripping a leading byte order mark — never by comparing timestamps, because a checkout rewrites timestamps and an encoding convention rewrites bytes without changing meaning. A file present on one side and absent from the other is drift of its own kind and is reported as such; before 2026-09-12 it produced no signal at all. The qualifier is part of the term: the bare word *drift* already means generated output no longer matching its source in this project, and the two conditions are unrelated.
  - **Correction (2026-10-31, `.claude/concepts/2026-10-12-dedupe-claude-config.md`, block 14):** the drift check, `plugin_doctor.py --drift`, reports the one-sided case as its own finding kind, `one-sided`: a file a declared list names that exists on one side only. Each finding carries an owner, `plugin` or `repo`. The owner is `repo` when the sync config's `repo_owned` list names the file. With `--ignore-repo-owned`, a finding whose owner is `repo` is printed as `reported` and does not count. A `one-sided` file in `repo_owned` is still a finding.
  - **Correction (2026-10-30, `.claude/concepts/2026-10-30-angular-tailwind-followups.md`):** `--drift` also compares Add-on documents (`content-differs` / `one-sided`) and reports a Disabled add-on hook still present as `disabled-hook-installed`.
  - **Correction (2026-11-01, `.claude/concepts/2026-10-31-warn-on-unshipped-hook-rows.md`):** `--drift` also reports `dangling-hook-row`, which is not drift because no plugin copy is compared. The doctor scans for it from the project alone, before and independent of the comparison, and lists it even when the comparison cannot run and the run exits 4.
- **Worktree segment** *(2026-09-28)* — the part `.claude/worktrees/<name>/` of a path, where each of the three parts is one whole path component. It marks where a path crosses from the repository into a nested checkout. It is recognised with either separator and may occur more than once when worktrees nest. `.claude` is compared literally, apart from case. `worktrees` is compared after folding its Windows alias spellings: trailing dots or spaces, and a `:stream` suffix. A path that ends at `<name>` also contains one, and that path is the worktree root itself. `worktreesX`, a bare `.claude/worktrees` and `foo.claude/worktrees` contain none. "Segment" is the word the guards' own lists already use for a path part (`BYPASS_PATH_SEGMENTS`). Recognised by `.claude/hooks/_project_paths.py`.
- **Checkout-equivalent path** *(2026-09-28)* — a path with every **Worktree segment** removed and its separators turned into forward slashes, keeping the case of what remains. It is the path the same file would have in the main checkout. Before the search, runs of separators collapse to one and `.` components are dropped, except a leading network-path pair and a leading `.`. A path with no worktree segment comes back as its raw text with forward slashes and nothing else changed, so no main-checkout verdict can move. Each path guard tests its segment or substring bypass list against this path. Filename, extension and "Files to touch" tests keep reading the raw path. Produced by `checkout_equivalent_path` in `.claude/hooks/_project_paths.py`.
- **Enclosing worktree root** *(2026-09-28)* — the directory that ends at the innermost **Worktree segment** of a target path, or none when the path holds no worktree segment. It is never a sibling worktree. The concept gate and the bash gate add `<root>/.claude/concepts` to that one target's contract search, so a worktree's own approved contract still covers its source. It is not a rank in `claude_roots()` and is computed from the path text alone. Produced by `enclosing_worktree_root` in `.claude/hooks/_project_paths.py`.
- **Fallback mode** *(2026-09-28)* — the state a guard hook is in when a shared helper function it needs is unavailable, whether the helper failed to import or imported without that function. The guard then uses its own small inline copy of the rule. That copy must never restore the behaviour the rule replaced, must leave the repair path open, and its block message names the missing helper and the path looked for. For the worktree path guards, fallback mode blocks worktree source and keeps every `.claude/` path allowed. The **Gate launcher**'s copy differs: it blocks main-checkout `.claude/` paths too, keeps worktree paths editable, and wraps its helper call so that a helper that throws also lands in fallback mode. Distinct from failing open, where a crashed guard allows everything. See **Guard fallback mode** in `MECHANISMS.md`.
- **Install mode** *(2026-10-04)* — how the plugin's assets reached a consuming project, decided only from files on disk. Five values: `plugin-source` (the project is the plugin's own checkout), `both` (the plugin is installed and enabled and the hooks are also vendored), `plugin` (installed and enabled, nothing vendored), `vendored` (the project's `.claude/hooks/concept-gate.py` exists and no enabled install exists), `none` (neither). An installed plugin that is switched off is refused as `plugin-disabled` unless a vendored copy exists, in which case the mode is `vendored`. "Enabled" is read from the user, project and local settings layers only; managed settings are not read. Only entries for `agentic-auto-improve@<marketplace>` are consulted, so any other installed plugin is ignored.
- **Placeholder slot** *(2026-10-04)* — a project-profile slot whose value is still the template's italic `*(...)` prose, or an empty cell, or whose row is missing. It is the only kind of slot `/auto-improve-finish-install` may write. A slot holding any other value, `none` included, is an **authored slot** and is never changed; a proposal that differs from it is advice only.
- **Registration key** *(2026-10-04)* — the identity of one hook registration, used to decide whether it is already present: the event name, the hook file name, and any arguments after the file name. Example: `Stop` + `memory-pager.py` with no arguments. The same file registered with an extra argument would be a different key. The matcher and the path prefix are deliberately not part of it, and both the string form and the `command` + `args` form of a registration produce the same key.
- **Working agreement** *(2026-10-05)* — one standing rule about how the assistant works with the user, kept as one markdown file in an agreements folder and delivered as context at session start by `working-agreements.py`. It is guidance read by the model, not a check: nothing blocks when it is ignored. A rule that a hook also enforces may still be an agreement, because the hook sees only part of it. A project's own instructions and a skill's explicit gate that requires asking the user win over any agreement. Distinct from a **Guard rules file**, which configures a hook rather than instructing the model. See **Session-start context delivery** in `MECHANISMS.md`.
- **Shipped agreement** *(2026-10-05)* — a **Working agreement** that ships with the plugin in its own `.claude/agreements/` folder and is labelled "from the plugin" when delivered. It names no project, no person, no machine path and no incident date, and a test checks this. Delivered only under a plugin install or in the plugin's own checkout; a vendored copy of the hook delivers nothing.
- **Project agreement** *(2026-10-05)* — a **Working agreement** a consuming project keeps in its own `.claude/agreements/` folder, delivered after the shipped ones and labelled "from this project". A project can add agreements but never replace one: a file whose name matches a shipped file's name, ignoring case, is skipped and logged as `shadows-shipped`. A project title cannot carry a "from the plugin" label, and a project body cannot add headings of its own.
- **Always-kept agreement** *(2026-10-05)* — the shipped plain-language agreement, and nothing else: the one **Working agreement** the size limit never drops. The guarantee belongs to the shipped text only. No configuration and no project file can extend it to another agreement or take its place.
- **Contract Delivery** *(2026-10-05)* — the merge, verified by GitHub, of one pull request into the repository default branch that carries a contract's handoff blocks. It is never inferred: the operator records it with `--record-delivery`, and the script refuses unless the pull request is the one the contract's own brief names. Stored as the contract's delivery record beside its completion records. For a contract with two or more mergeable blocks the delivery is the parent branch's landing pull request; a delivery made any other way is still recorded as it is, and `--status` reports the layout warning `single-branch-delivery`.
- **Completion Verdict** *(2026-10-05)* — the script's ordered reading of whether a contract has nothing pending, from a closed set (`not-eligible`, `already-implemented`, `pending`, `not-evaluated`, `unverifiable`, `would-flip`, `flipped`), with the reasons, remedies and next command for every unmet condition. It is not a move of the Next Command; it is printed as its own line before it.
- **Gate Output** *(2026-10-05)* — the small machine-readable file a review gate writes beside its review artefact (`<artefact stem>.gate.json`), carrying only what supersedes what and the gate's outcome per Review checklist item. It is the Review artefact mechanism's own sibling-file seam; the markdown stays the human surface.
- **Not-performed item** *(2026-10-05)* — a verification the owner declares skipped or impossible, at the one confirmation (`--skipped <text>`): a Review checklist line or a check outside the checklist. It needs a Disclosure line before the contract can flip, and a matching checklist line stays unchecked with "not performed". A line nobody declares and no Gate Output supports is not one: it stays unchecked with "no structured evidence" and never blocks.
- **Disclosure line** *(2026-10-05)* — the fixed line `Not performed (<contract-slug>): <declared text>` on the contract's Tracking Issue, posted by the skill after the owner's confirmation.
- **Tracking Issue** *(2026-10-05)* — the one GitHub issue per contract that tracks its follow-ups and disclosures: the contract's `**Tracking issue:**` header line, else the single issue number its follow-up stubs carry.
- **Records pull request** *(2026-10-05)* — the small docs-only draft pull request, on branch `docs/<contract-slug>-records` (never `task/...`), that carries the git-tracked files the loop writes after a merge: completion records, the delivery record, and on a flip the contract and the brief. Never the state store, which is git-ignored.
- **Main checkout** *(2026-10-11)* — the repository's original checkout: its `.git` entry is a directory, or a file whose git directory holds no `commondir` file. Every session that starts without choosing a worktree lands here, so it is shared by all of them. The main-checkout guard refuses edits and tree-changing commands aimed at it. Defines a word the registry already used undefined (**Worktree segment**, the path-resolution entry in `MECHANISMS.md`). The issue that asked for the guard says "primary tree"; this registry uses "main checkout". Introduced by `.claude/concepts/2026-10-07-worktree-isolation-by-default.md`.
- **Flat worktree** *(2026-10-11)* — a linked worktree whose root sits directly in `<main checkout>/.claude/worktrees/`, so its path holds exactly one **Worktree segment**. Its folder is named `<YYYYMMDD>-<action>-<slug>`, at most 60 characters. A worktree inside another worktree is nested, never flat. Produced by `.claude/scripts/flat_worktree.py`. Introduced by `.claude/concepts/2026-10-07-worktree-isolation-by-default.md`.
- **Delivery cleanup** *(2026-10-15)* — the automatic removal of the worktrees and local branches that belong to one work item, and of its remote branches only when the caller passes `remove-remote`. It acts only once the contract reads `Status: implemented` at `origin/<default>` and every sub-task has a GitHub-verified completion record there, and it removes nothing whose commits are not already in `origin/<default>`. It runs on every `/pr-merged` and `/advance` call and reads "not delivered yet" until then. Performed by `.claude/scripts/cleanup_delivered.py`. Introduced by `.claude/concepts/2026-10-15-auto-cleanup-delivered-worktrees.md`.
- **Owned set** *(2026-10-15)* — the branches and worktrees that belong to one work item and nothing else: the linked brief's `branch:`, `task/<slug>/<id>` for each sub-task, `docs/<slug>-records`, and the worktrees that hold one of those branches, sit at the brief's `worktree:` path, or carry this slug's advance-worktree name and no other contract's. Decided by branch or exact path, never by folder name alone. Introduced by `.claude/concepts/2026-10-15-auto-cleanup-delivered-worktrees.md`.
- **Standing tree** *(2026-10-15)* — a worktree that the running session, its shell or another process currently holds, by standing in it or keeping a file open in it. Delivery cleanup defers it and leaves it entirely untouched; the next call from outside removes it. Detected by the session's own folders (the script's working directory, `CLAUDE_PROJECT_DIR`, `--from`) on every platform and, on Windows only, by a rename probe that cannot see a Git Bash shell. Introduced by `.claude/concepts/2026-10-15-auto-cleanup-delivered-worktrees.md`.
- **Landed untracked file** *(2026-10-17)* — an untracked file in an owned worktree that git would store as exactly the blob `origin/<default>` holds at the same path: that path is an ordinary file there (mode 100644 or 100755), the file is not a link and sits under no linked folder of the tree, and `git hash-object` with the clean filters and line-ending conversion git applies when staging gives that blob's id. A file that differs from the blob only in CRLF versus LF under a conversion setting counts as landed; any content change does not. Delivery cleanup deletes such files one at a time, last, each re-hashed just before its delete, then removes the tree without force. Every other untracked file is unsaved work and keeps the tree. Introduced by `.claude/concepts/2026-10-17-worktree-removal-untracked-identical.md`.
- **Outside every project** *(2026-10-17)* — a path where neither the absolute path as written (links not followed) nor its resolved form has a project marker (`.git`, `CLAUDE.md`, `package.json`, `pyproject.toml`, `*.sln`) on itself or any ancestor, and every existing ancestor could be checked and listed without error. The concept gate does not gate such a path. Not the same as `tree_kind`'s `outside-repository`, which reads path text and looks for `.git` only: a folder with a `CLAUDE.md` and no `.git` is `outside-repository` yet not outside every project. Neither term stands in for the other. Introduced by `.claude/concepts/2026-10-17-worktree-removal-untracked-identical.md`.
- **Merge direction** *(2026-10-11)* — which branch a pull request may target. A sub-task's pull request targets its declared parent branch; the parent's targets the default branch, and only while no sub-issue and no pull request into the parent is open; a **Cross-Repository Pull Request** targets that repository's default branch. Checked before a pull request is opened, retargeted or merged, by `.claude/scripts/merge_direction.py`. Introduced by `.claude/concepts/2026-10-07-worktree-isolation-by-default.md`.
- **Gate launcher** *(2026-10-11)* — the small registered program (`.claude/hooks/gate-launch.py`, a stub, and its body `_gate_launch.py`) that reads one hook payload, runs the main-checkout guard, which also runs the **Merge direction** check for `gh pr` commands, and only then runs the named gate (`concept-gate.py` or `bash-gate.py`) in the same process. A failure in its own code is a block. Introduced by `.claude/concepts/2026-10-07-worktree-isolation-by-default.md`.
  - **Correction (2026-10-31, `.claude/concepts/2026-10-12-dedupe-claude-config.md`, Revisions 3 and 4, block 14):** the plugin now registers the launcher on shell commands too, `gate-launch.py concept-gate.py` on `Bash|PowerShell`, beside its edit row. `concept-gate.py` allows any tool that is not an edit, so on a shell command only the main-checkout guard and the **Merge direction** check act. Neither gate row is this repository's any more. `bash-gate.py` is now the opt-in strict add-on, and its install registers it directly, not through the launcher. The guard reads shell write targets with the default helper `_shell_write_targets.py`, which it shares with the strict gate.
  - **Correction (2026-11-07, `.claude/concepts/2026-10-12-dedupe-claude-config.md`, Revision 9, block 38):** the Gate launcher is not the **Project hook launcher**, and neither replaces the other. The Gate launcher is a registered file. It accepts only two named gates from its own folder, runs the main-checkout guard first, skips the gate on PowerShell, re-encodes the input and drops extra arguments. The Project hook launcher is program text carried inside a project's own hook row. It runs any project hook unchanged and adds no guard of its own. `_gate_launch.py` was left as it is.
- **Design foundation** *(2026-10-22)* — the set of design rules every page of a project obeys, whatever kind of page it is: theme polarity per application, the token bridge, the inline-style ban, accessibility, motion and the never-do list. It exists once, in `skills/website-design/references/foundation.md`; `application-design` reads it from its sibling folder before its own layer, and neither skill restates it. Introduced by `.claude/concepts/2026-10-22-webdesign-plugin-skills.md`.
- **Design surface** *(2026-10-22)* — the kind of thing being designed, one of two values: *application screen* (a data-dense, always-on product screen, designed with `application-design`) or *website page* (a marketing or content page, designed with `website-design`). Per-application differences come from project profile slots, never from more skills. Introduced by `.claude/concepts/2026-10-22-webdesign-plugin-skills.md`.
- **External skill reference** *(2026-10-22)* — a mention, in any asset this plugin ships, of a skill owned by another plugin. It carries the fully qualified name `<plugin>:<skill>` (or, for a host built-in skill no plugin ships, the bare name and the words "host built-in"), the word *advisory*, the precedence (this plugin's rules and the project's `review.documents` win), and what the asset does when that skill is absent: it continues without it. It is never a hard dependency. Distinct from an internal reference to this plugin's own skills or agents, written `agentic-auto-improve:<name>`, which may be required. Rule text: `CONTRIBUTING.md` → "Referencing another plugin's skill". Introduced by `.claude/concepts/2026-10-22-webdesign-plugin-skills.md`.
- **Parent Branch Delivery Rule** *(2026-10-30)* — the rule that a contract whose handoff has two or more mergeable blocks (a review gate is one) is always delivered through a parent branch: the `branch:` of the contract's own Work Item Brief. Every sub-task branch is cut from it, every sub-task pull request targets it, and one landing pull request moves it to the default branch. Nobody chooses this layout. The plugin version is never raised in a sub-task pull request; it is raised once, during the landing.
- **Layout defect** *(2026-10-30)* — a contract-level reason, from a closed set (`no-parent-branch`, `parent-is-default`, `ambiguous`, `no-parent-issue`, `sub-task-raises-version`), why a multi-sub-task contract cannot be dispatched or approved under the **Parent Branch Delivery Rule**. Each carries a remedy. It blocks dispatch and approval only; it never refuses a recording and never enters a stored record.
- **Landing version raise** *(2026-10-30)* — the single raise the landing commits on the parent branch after merging the default branch: minor + 1, patch reset to 0, relative to the default branch's version. Under `landing: manual` the operator makes it.
- **Layout warning** *(2026-10-30)* — a fact-derived entry of `layout_warnings` in `--status --json` and the Landing Report: `single-branch-delivery` when a completion record has `base_is_default: true` or a `base_ref` other than the parent branch, or a known one-branch Delivery Candidate exists; `unverifiable` when `origin/<default>` could not be read. It is never stored in a record and blocks nothing: not recording, completion, dispatch or landing.

- **Add-on** *(2026-10-30)* — a set of files the plugin ships under `.claude/addons/<name>/` and never registers itself; a project gets them only through the add-on's install skill.
  - It declares no kill switch. It is on when installed, and its uninstall skill is the normal way to turn it off.
  - When one of its hooks cannot run, the user removes that hook's row from `.claude/settings.json` by hand, by the route its README table gives for that hook. A hook cannot run when its file is missing (Python exits 2 with its own error) or when a helper fails to import (the hook's own message).
  - The default hooks' switches, such as `CLAUDE_CONCEPT_GATE` read by `concept-gate.py`, are not add-on switches.

The row's `if: "Bash(codegraph *)"` admits more than this (it matches each sub-command of a compound line and strips leading `VAR=value`), so the tracker's own test is what narrows it; `codegraph.exe`, `codegraph.cmd`, path forms, `npx`, compound lines and the PowerShell tool are not the route.
- **Counted command** *(2026-11-07, issue #295)* — the closed set of `codegraph` subcommands that mirror a CodeGraph MCP tool: `query`, `explore`, `context`, `node`, `callers`, `callees`, `impact`, `files`. Every other subcommand (`status`, `init`, `index`, `sync`, `serve`, `daemon`, …) is not counted. An exit 0 is counted even when the answer is "no results" (the output is never read).
- **Session server process** *(2026-11-07, issue #295)* — a descendant, within four levels, of this session's **Hook host process** (the hook's own ancestor chain excluded) whose command line, with quotes and `^` removed, holds the tokens `serve` and `--mcp` and a CodeGraph token (a token whose base name minus `.exe`/`.cmd`/`.bat`/`.js`/`.mjs`/`.cjs` is `codegraph`, or whose path has a `codegraph` folder). On Windows one server is three such processes (the `cmd /c` shim and two `node` processes). A candidate with `serve` and `--mcp` but no CodeGraph token, or an unreadable command line, makes the probe undecidable. Not the CodeGraph daemon, which serves every session of an index root.
- **Hook host process** *(2026-11-07, issue #295)* — the nearest ancestor of a hook process that is not a Python interpreter or launcher and not a shell (`python`, `python3`, `pythonw`, `py`, `bash`, `sh`, `dash`, `zsh`, `cmd`, `powershell`, `pwsh`, `env`), within eight hops. It is trusted only when its image is in the known-host set, today `claude` (the native `claude.exe`, recorded by live trial on 2026-11-07); any other image (such as `node` for an npm install) makes the probe undecidable.
- **Connection notice** *(2026-11-07, issue #295)* — the `codegraph` reset hook's per-prompt message (`systemMessage` for the user, the same text as `additionalContext` for the model) that this session has no **Session server process** although the server is configured with a `command` and a Project index exists. It names `/mcp` and the **Command-line route**, echoes nothing from the prompt, ends by yielding to a project instruction or a skill's gate that forbids shell commands, and is silent for a subagent, on a healthy session, when the probe is undecidable, and on any error or a spent 100 ms budget. It never blocks and no switch turns it off.
- **Project hook launcher** *(2026-11-07)* — a small standard-library program written inside a project's hook row, as `py -3 -c <its text> <class> <script> …`. It runs the project's hook from the session's project folder in the same process. When that folder is gone, it runs the hook from the main checkout instead. When the hook is in neither place, it blocks (class `block`, written only on `PreToolUse`) or warns (class `warn`, every other event). While the project folder exists, it changes where a hook is found, never what the hook decides. During a fallback the hook still sees the removed folder named as the project, so the database guards apply their stricter rules. Its text has one source of truth, a constant in `_project_paths.py`. Any change to the text raises the version in its first-line marker. Distinct from the **Gate launcher**, a registered file that runs the main-checkout guard before one of two named gates. See the mechanism entry in `MECHANISMS.md`. Introduced by `.claude/concepts/2026-10-12-dedupe-claude-config.md` (Revision 9).
