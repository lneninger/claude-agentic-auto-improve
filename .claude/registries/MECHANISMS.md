# Reusable Mechanism Registry

> **Purpose:** catalog every proven reusable pattern across the projects Claude works on. The `data-architect` agent reads this file BEFORE proposing anything. Extension over creation is the default. Creating a new mechanism requires written justification in the concept contract.
>
> **Maintained by:** `fullstack-code-reviewer` appends entries when a PR introduces a genuinely new reusable pattern. The `data-architect` appends entries when a concept contract promotes a new mechanism from draft to implemented.
>
> **Structure:** two tiers. Universal patterns apply to every project. Project sections hold codebase-specific mechanisms. The data-architect always consults BOTH tiers.

---

## Universal Patterns (cross-project)

These patterns are language- or framework-level and should be the first thing considered before inventing anything new.

- **CodeGraph (semantic code knowledge graph)** — primary codebase investigation mechanism. Index at `<project>/.codegraph/codegraph.db` (built/refreshed by the `codegraph` CLI). Tool surface: `mcp__codegraph__codegraph_{search,node,callers,callees,impact,files,status}` (main session, cheap) and `mcp__codegraph__codegraph_{explore,context}` (Explore subagent only, heavy — they return full source sections). Decision table: `.claude/references/codegraph-decision-table.md` — full routing, worked examples, gate mechanics and the known failure modes. Written 2026-08-25 during the Claude-setup merge; it had been cited-but-absent since at least 2026-08-24, along with the whole `~/.claude/references/` directory. The `ui-ux-pro-max/` citation in `CLAUDE.md` was resolved in the same pass — not by recreating the phantom catalog but by repointing to the design-pattern document named in the project profile's `review.documents` slot (authoritative) plus the `/dataviz` skill. **Per-turn enforcement**: `~/.claude/hooks/codegraph-first-guard.py` (PreToolUse on `Read`/`Grep`/`Glob`) blocks source-path investigation until a `mcp__codegraph__*` call has set the sentinel `<cwd>/.claude/.codegraph-used-this-turn` (created by `codegraph-turn-tracker.py` PostToolUse, deleted by `codegraph-turn-reset.py` UserPromptSubmit). Bypass: `CLAUDE_SKIP_CG=1` (user only). Lifecycle: `codegraph sync-if-dirty` on SessionStart/Stop, `codegraph mark-dirty` on Edit/Write. Extend by: when a new language/framework is added, ensure `.codegraph/config.json` includes its extensions; when a new investigation pattern recurs, add a row to the decision table.

- **Disposable migration dry-run DB** — the only safe way to verify a migration applies cleanly from a fresh schema. Connection-string DB-name suffix MUST match the disposable allow-list: `_DryRun_<guid>`, `_MigrationVerify_<guid>`, `_Sandbox`, `_Scratch`, `_Throwaway`, `_Test_<hex-guid>`, or `_e2e_<hex-guid>`. Created in a per-test setup; dropped in teardown. NEVER shares a connection string with dev/prod. Enforced by `~/.claude/hooks/db-destructive-guard.py` which BLOCKS destructive ops (`dotnet ef database drop`, `DROP DATABASE`, `EnsureDeleted`, etc.) against non-disposable DB names. Override path: human user sets `CLAUDE_DESTRUCTIVE_DB_OK=1` for a one-shot exception. Reference incident: 2026-05-06 lneninger / strategies wipe — a sub-agent ran `dotnet ef database drop --force` against the dev connection string to verify a migration.

- **Read-only forensic DB connection** — all research / inspection / "what's in the DB" queries against a project DB MUST use connection-layer read-only enforcement: `ApplicationIntent=ReadOnly` (SQL Server) / `default_transaction_read_only=on` (Postgres) / `?readOnly=true` (Mongo) AND wrap the session in `BEGIN TRAN; … ROLLBACK;` for redundant safety. Enforced by `~/.claude/hooks/db-research-readonly-guard.py`: any opened DB connection with write keywords (`INSERT|UPDATE|DELETE|MERGE|CREATE|ALTER|DROP|TRUNCATE|UPSERT`) and no read-only flag is BLOCKED.

- **Response envelope pattern** — wrap all API results in a tagged success/failure shape (`ApiResponse<T>`, `Result<T,E>`, etc.). Never return raw objects. Extend by: returning the project's envelope type from new endpoints.
- **Signal state service (Angular)** — private writable signals inside an injectable state service, exposed as `.asReadonly()`. Extend by: creating a new state service following the convention at `core/state/`.
- **Observable → signal bridge** — convert RxJS Observables to signals via `toSignal()`, clean up with `takeUntilDestroyed(destroyRef)`. Never mix async pipe with signal-driven templates.
- **Dispatcher pattern** — priority-routed external calls with a capability enum and provider fallback. Extend by: adding a capability enum value and implementing it on the matching providers.
- **Field resolver pipeline** — data keys → `IFieldResolver` → `ContextResolver` → `ConditionEvaluator`. Generic evaluation pipeline usable for any context-driven rule engine. Extend by: adding a field key and a resolver; no new evaluator needed.
- **Port / Adapter (Clean Architecture)** — domain declares interfaces; infrastructure supplies adapters. Extend by: adding a new adapter to an existing port before declaring a new port.
- **EF Core `AsNoTracking()` on reads** — all read queries must use it; the mechanism is the project's read-only repository base class.
- **JSON columns via `HasConversion`** — store complex value objects as JSON in a single column with `System.Text.Json`. Extend by: adding a property and registering the conversion in `IEntityTypeConfiguration`.
- **Quartz job + dispatcher** — background ingestion pattern: Quartz job calls `IExternalDataDispatcher`, never a specific provider directly.
- **SignalR hub event pattern** — typed event payloads pushed from a hub to clients on state transitions. Extend by: adding a new method to the hub contract and wiring from the emitting service.
- **Scroll-edge CSS primitive (Angular)** — `scroll-edge` / `scroll-edge-content` / `scroll-edge-header` global classes for scrollable containers. Never inline `overflow-y-auto` / `sticky` / `relative`+`absolute` combinations for scrollable tables or lists.
- **Batched-IN query pattern** — for EF Core queries that filter by a key set which may exceed the database's per-statement parameter limit (SQL Server caps at ~2100), split the key set into chunks of ≤2000 and execute one server-side query per chunk, concatenating the results. Implementation: `BatchedInQuery.ExecuteAsync<T, TKey>(keys, queryFactory, batchSize = 2000, ct)` — caller supplies a factory that turns a batch into an `IQueryable<T>` and retains full control over `AsNoTracking()`, projections, and additional filters. **Never** use the naive `.Where(e => hugeSet.Contains(e.Key))` for sets whose size might exceed ~2000 — it generates an oversized `IN()` clause that fails with a TDS protocol error. Also **never** fall back to `.ToListAsync()` + in-memory filter as a workaround — that defeats pagination and wastes memory on the full table. Extend by: for key sets so large that even batched concatenation is wasteful (100k+), add a temp-table-based variant with bulk-insert + JOIN.
- **Startup task runner pattern** — for fire-and-forget startup work (LLM bootstrap, quota state load, scheduler registration + catch-up, dispatcher DB init), implement `IStartupTask` (Domain port) and register via `services.AddStartupTask<T>()`. A single `StartupTaskRunnerHostedService` (inheriting `BackgroundService`) executes every registered task once at startup, in registration order, with a fresh DI scope per task and centralised exception isolation — a failure in one task does NOT cancel the others, exceptions are logged with the task's `Name`, and the runner continues. **Never** sprinkle `_ = Task.Run(async () => { try { ... } catch { log } })` blocks through `Program.cs`: that pattern silently swallows exceptions, captures scoped services against the root provider, and is impossible to test or reason about as a unit. Tasks check their own feature flags inside `ExecuteAsync` and early-return if disabled — no conditional registration in `Program.cs`. Constructor-triggered fire-and-forget DB loads (the "constructors can't be async" workaround) should also be moved to a startup task that calls a public `InitializeAsync()` method on the service. Extend by: add a new task class implementing `IStartupTask`, register one line. For tasks that MUST complete before the HTTP server accepts requests, use `IHostedLifecycleService.StartingAsync` instead — the runner's `BackgroundService` base runs concurrently with the server.
- **Python sidecar package layout (FastAPI router + lazy-loaded heavy deps + dependency overrides)** — a thin Python package mounted on a host FastAPI app via `app.include_router(...)`. The package exposes one `APIRouter` whose endpoint dependencies (`Depends(get_X)`) resolve to placeholder functions that raise `NotImplementedError` at module-load time. The host `main.py` wires real implementations via `app.dependency_overrides[get_X] = lambda: Y`, where `Y` is a lazy-loaded singleton with `threading.Lock`-protected double-check locking. Heavy imports (`torch`, `d3rlpy`, `transformers`, `pyarrow`) live inside method bodies — never at module top — so package import + uvicorn boot stay fast, and tests can mock heavy deps at `sys.modules` without paying the import cost. Two concrete users in this codebase: `python/scalping_llm/` (chat-tool LLM training + inference) and `python/scalping_strategy_rl/` (offline-RL policy training). Extend by: add a third sidecar mounted under a new `/api/<domain>/*` prefix on the same uvicorn process — never spin a separate uvicorn for new offline-Python work; co-tenant on the same process and reuse the same dependency-override seam. **Never** import one sidecar's modules from another sidecar; that defeats the lifecycle decoupling that makes either replaceable.
- **Real-vendor sentinel test pattern** — for any pinned third-party SDK whose public-API shape your production code depends on, write a sentinel test module that asserts the SDK's surface AT THE PINNED VERSION exists. Pattern: an isolated `tests/integration/conftest.py` that does NOT replicate the unit-test mocks; a `real_<vendor>` fixture that `sys.modules.pop`s the parent conftest's mock entries into a `stashed` dict, `importlib.import_module`s the real package inside `try`, yields the real module, and `finally`-restores the mocks unconditionally so other tests are unaffected. Required assertions per vendor symbol the production code references: `hasattr(<module>, "<expected_symbol>")` (positive) — and **negative** `not hasattr(<module>, "<known_absent_symbol>")` for siblings that must NOT come back, paired with a docstring explaining the recovery procedure if the negative ever fails (a vendor restoration). Lock in vendor-specific quirks via behaviour assertions (e.g. `<Config>.create()` raises `NotImplementedError` in some 2.x APIs). Mark the test module with `pytest.importorskip("<vendor>")` so CI environments without the SDK installed skip gracefully; local runs WITH the SDK installed catch real drift. Concrete user: `python/scalping_strategy_rl/tests/integration/test_d3rlpy_api_pinned.py` — caught Phase D's IQL→BCQ vendor-API drift that the unit-test mocks (which auto-fake every attribute access) had silently masked across 81 passing tests. Extend by: any external SDK pinned in `requirements.txt` / `pyproject.toml` / `*.csproj` whose drift would silently break a wrapper.
- **Paged read-response envelope (`PagedResponse<T>`)** — generic immutable record at Common/PagedResponse.cs, in the domain project named by the `backend.roots` slot of `.claude/project-profile.md`: `{ Items: IReadOnlyList<T>, TotalCount: int, Offset: int, Limit: int }` with `init` setters. Wraps any paginated read endpoint's response so callers receive both the page slice AND the total count for "Page X of Y" rendering. Lives in Domain (NOT Services) — Domain is the no-deps layer; Services + Persistence + API can reference it without circular-dep risk. Universal candidate for any future paginated read; first concrete consumer is Phase G's `GET /api/run-pairs/ended`. NSwag emits a concrete TypeScript interface per closed-over type-arg (e.g. `PagedResponseOfRunPairListItemDto`) — TS does not generate generics. Extend by: returning `PagedResponse<T>` from any paged read service method; controller wraps in `ApiResponse<T>`. **Never** invent a parallel `*Page<T>` / `*PaginatedResult<T>` shape — collapse to this one envelope.

- **SystemConfigEntity + ISystemConfigService** -- generic runtime-toggleable key-value config table. Universal: every production system eventually needs runtime feature flags without appsettings.json restarts (this is why it is promoted to the Universal tier rather than staying project-scoped). Single-table pattern: {Key: string PK, Value: string (max 4000), Description?, Category?, UpdatedAtUtc, UpdatedByUserId}. Typed read accessors via GetBoolAsync/GetStringAsync/GetIntAsync; write via SetAsync(key, value, updatedByUserId, ct). Read-through IMemoryCache (60s sliding TTL) with write-invalidate on SetAsync so kill-switches take effect within one TTL window. Admin REST endpoint GET/PATCH /api/admin/system-config/{key} (owner: AdminSystemConfigController). DO NOT log raw Value on write -- log only {Key} + {UpdatedByUserId} to avoid leaking future secret-holding flags (Q19 pattern: the table is opened for arbitrary future flags, so any flag may eventually hold a token or secret). Extend by: add GetJsonAsync<T> for structured values; add per-category cache buckets; add an audit-log emit on write (follows IAuditLog pattern). Project-specific impl: SystemConfig/SystemConfigService.cs in the services project and Repositories/SystemConfigRepository.cs in the persistence project, both named by the project profile's `backend.roots` slot.

- **Adaptive Engineering Journal** — append-only log of lessons learned from concept-contract critiques and post-implementation reviews. `.claude/registries/JOURNAL.md`. Two-tier (Universal + per-project) mirroring `MECHANISMS.md` / `VOCABULARY.md`. Read by `data-architect` (Step 1, alongside MECHANISMS / VOCABULARY / INTEGRATION) and `contract-critic` on every run; every entry's `Apply when:` pattern is matched against the active draft contract. Appended by three triggers, each tagged in the entry: (1) `contract-critic` findings that the user confirms during `/design-first` Step 3 → `Trigger: pre-approval critic`; (2) `fullstack-code-reviewer` when implementation justifiably diverged from the contract or a contract assumption was falsified → `Trigger: post-impl divergence`; (3) `/journal-add` skill for any out-of-protocol lesson (production incident, debugging insight) → `Trigger: manual`. Entry shape is fixed (Title / Trigger / Source contract / Lesson / Apply when / Tags) and lives in the file's header. Extend by: add a new entry under the matching project section (or Universal tier for cross-project lessons) — NEVER reorder or rewrite past entries; if a lesson is refined, append a new entry referencing the old by date+title. The `## Lessons referenced` section in every concept contract back-references the entries that influenced its design.

- **Two-layer Claude path resolution** — the single resolver every `.claude/` hook and workflow script uses to locate Claude *data* (registries, concept contracts, north-stars, the area map, the contract-accuracy ledger, the derived-scan cache). Layer 1 is `.claude/hooks/_project_paths.py`: `claude_roots()` returns an ordered candidate list and every locator (`registry()`, `concepts_roots()`, `area_mapping_path()`, `accuracy_state_path()`, `north_stars_roots()`, `cache_dir()`, `first_populated_dir(roots, pattern)`, `state_dir()`, `logs_dir()`, `hook_file()`) is a **zero-argument call-time function** — never a module constant and never a default argument, or the path is captured at import and neither a test nor a different checkout can redirect it. Layer 2 is `.claude/scripts/_claude_paths.py`: `scripts/` and `hooks/` are siblings and a script under `.claude/scripts/` launched directly by the interpreter gets only its own directory on `sys.path[0]`, so the bridge resolves `hooks/` from `Path(__file__)`, **appends** it to `sys.path` (never `insert(0, …)`, so the scripts' own directory keeps import priority) and re-exports the locator surface. Selection rule: *first root that actually contains the thing sought* (mirrors `registry()`'s `is_file()` test and `first_populated_dir()`'s glob test) — never "first root that exists", which lets an empty directory win and report zero, and never a union of roots, which leaks another checkout's contracts into this one's inventory. Two failure classes, deliberately different: a missing **data file** at a correctly-resolved root fails OPEN (neutral value, exit 0, the critic still runs); a missing **resolver** raises `ImportError` naming the path it looked for — the repo is malformed and a silent home-directory fallback there would recreate the defect the layer exists to remove. Runtime state (`logs/`, `state/`) deliberately resolves through `project_dir()` alone, not the root search — it is machine-level, not repository content. Tests: `.claude/scripts/tests/test_script_path_resolution.py`. Extend by: add one locator function to `_project_paths.py` and one re-export line to `_claude_paths.py`; a new script under `.claude/scripts/` inherits correct resolution simply by importing from the bridge. **Never** write `Path.home() / ".claude" / …` in a script or hook — the 2026-08-25 migration emptied that tree and seven scripts read it silently for a day (work item #35).

- **Plugin registry ownership model** — the label that says whether a setup file under `.claude/` is owned by the plugin repository, and therefore replaceable on sync, or owned by the consuming project, and therefore never touched. Ownership is expressed by an `ownership_tier` field on the tree entry in `.claude/.sync-config.json`, plus that tree's `files` array. It is NOT expressed by where a file sits on disk. **This is a correction, not a restatement.** Until 2026-09-12 the model said ownership was a directory: generic content was copied into `plugin-managed/` subdirectories while the originals stayed where they were, so the repository carried two copies of thirty-five files, nothing read the copies, and `.claude/settings.json` pointed only at the originals. A copy in a subdirectory does not remove an original — it creates a second one that drifts. The three subdirectories are deleted and there is now exactly one copy of every file. A file under `.claude/agents`, `.claude/skills`, `.claude/hooks`, `.claude/scripts`, `.claude/templates` or `.claude/references` that no tree's `files` array names is a **local asset by default**: it stays put and is never synced. The default points the safe way deliberately — a misclassified local file is invisible, while a misclassified generic file lands in every consuming project. Extend by: add a path to a tree's `files` array, or add a tree. Promoting a local file later costs one line plus the project-name check passing.

- **Bidirectional sync with manual conflict resolution** — `tools/sync-plugin.cmd`, delegating to `tools/sync-plugin.ps1`, propagates changes in both directions between a consuming repository and its plugin repository. Every synced tree is bidirectional; the three direction values (`bidirectional`, `plugin-to-repo`, `repo-to-plugin`) remain defined so a future tree can use another. Protection against pushing project content into the plugin is the **project-name check**, not a direction rule. On divergence the script writes `.claude/.sync-state/conflicts.json` and exits 2; the developer resolves and re-runs. Exit codes: 0 success, 2 conflict, 3 unresolved marker, 4 bad environment (including the plugin not being found), 5 project-name check failed. Plugin discovery is two layers, `CLAUDE_PLUGIN_ROOT` then the sibling directory, and exit 4 names both attempted locations. **Extend by: adding a tree, or a path to a tree's `files` array, in `.claude/.sync-config.json` — the script reads that file and builds its tree list, file lists and registry list from it.** *(That clause was false until 2026-09-12: the script never opened the configuration, its tree list was hard-coded, and adding a tree changed nothing at all.)* Three further defects were repaired in the same pass, each of which had made the tool useless rather than merely imperfect: the batch wrapper hit a top-level `goto :eof` and exited 0 without running anything; the PowerShell script carried a double-encoded character whose bytes decode to U+201C, which PowerShell accepts as a string delimiter, so the file could not be parsed; and it declared its own `-Verbose` switch, colliding with the common parameter. Two comparison defects were repaired too: it hashed raw bytes across a line-ending and byte-order-mark boundary, reporting eighteen conflicts that no edit could ever clear and training the operator to reach for `-Force`, the one path that silently overwrites real divergence; and it iterated only the differing files, so a file present on one side and absent from the other produced no conflict and exit 0 — the commonest way to break the rule the tool exists to enforce. Content is now compared with line endings folded and a leading byte-order mark stripped, and a one-sided file is reported as `ONLY_IN_MAIN` or `ONLY_IN_PLUGIN`.

- **Section-scoped registry sync** — `MECHANISMS.md`, `VOCABULARY.md` and `JOURNAL.md` are split into two tiers: Universal, which the plugin owns, and Project, which is local only. The sync compares and updates the Universal section alone; everything below the first `## Project:` line is never touched and never compared. **This is why a plugin mechanism entry must live in the Universal tier**: an entry below that heading can never reach the plugin, so filing a cross-project mechanism under a project heading silently guarantees no other project ever sees it. `INTEGRATION.md` is whole-file in the configuration and is the one registry with no Universal tier at all. Extend by: adding a registry file with the same two-tier shape to the `registries` tree; the boundary is header-based, so the structure must hold.

- **Project-name check** — the sync tool refuses to copy a file into the plugin when that file contains any string on the consuming project's token list. Token list at `.claude/.project-tokens.json`: one `tokens` array of literal strings — the repository name, the front-end application names, the database names, the source-project prefix, the vendor names the domain uses and the project's own handbook file names. Before the sync writes anything outbound it searches each file's text for each token, case-insensitively, and any hit stops the run with **exit code 5** and a report naming the file, the token and the line. It runs on the outbound direction only: a token found in a file arriving FROM the plugin means the plugin is already contaminated, and refusing the pull would leave the consumer stuck with the contaminated copy it already has. Deliberate false positives are declared, never suppressed by file: the optional `allowed` array holds exact strings with a one-line reason each, and an entry naming a file is not permitted, because that would exempt every reference added to the file later. This **replaces** the withdrawn "the plugin is authoritative for agents" rule, which protected the wrong direction — the plugin's own copies carry the consuming project's name, so a one-way pull pushed the contamination downstream into every consuming project. Extend by: add a string to `tokens`. Never add a file to an exemption list, because there is none.

- **Guard rules file** — the per-project settings a generic guard hook needs, in a JSON file named `<hook-name>.rules.json` beside the hook, so the hook body names no project and can be vendored unchanged. Five exist: `architecture-guard.rules.json`, `architecture-guard.exceptions.json`, `plain-language-guard.rules.json`, `db-destructive-guard.rules.json` and `integration-check.rules.json`. **The fail direction is per hook and must be stated in the file.** A hook that BLOCKS fails **closed**: `db-destructive-guard.py` with no rules file treats every database as protected and narrows its path allow-list, because a guard that fails open when its configuration disappears is worse than one that never moved. A hook that only WARNS may fail soft: `integration-check.py` with no rules file classifies nothing and warns about nothing, which costs a reminder rather than a safety layer. A rules file holding a project's own constants is a local asset and is not synced; a rules file that is generic in content is. Extend by: move a project constant out of a hook into its rules file, and prove the move with a control that exercises the guard **with the file renamed away**, not only with it present.

- **Project profile** — one file per consuming repository, `.claude/project-profile.md`, carrying every project-shaped fact a generic agent needs, one named slot at a time: backend roots, frontend roots and their theme polarity, test roots, migration root, authentication roots, safety-critical roots, primary review documents. A generic agent cites a slot by name instead of writing a literal path. Every slot is present even when empty, and an empty slot reads `none` rather than a blank line, because a blank line is indistinguishable from a slot somebody forgot. **An agent may cite only a slot the template declares**: an agent needing a fact no slot covers is a defect in the template, and the fix is to add the slot to the template in the plugin, in the same change, so every consuming project gains it at once. Never invent a local-only slot. Complements the project-name check rather than duplicating it: the check is a gate that says a file is contaminated and stops it, and the profile is the destination that tells the agent what to write instead. Blank template ships in the plugin at the same path. Extend by: add one row to the slot table, in the plugin, and cite it by name from the agent that needs it.
- **Two-tier registry with a generated complete index** — the shape that lets an expensive agent see every registry entry without reading the registries. Each registry is a thin top-level file holding only the Universal tier plus a pointer, with the project tier split into per-domain files beside it: `.claude/registries/MECHANISMS.md` over `MECHANISMS/{backend,frontend,data,trading,general}.md`, and the same for VOCABULARY and JOURNAL. `.claude/scripts/generate_registry_digest.py` walks all of them and writes `.claude/.scout-cache/registry-digest.md`, one line per entry carrying its title and a `file:line` reference, then re-opens every reference it just wrote and exits non-zero if any fails to resolve — a stale digest fails loudly instead of misdirecting a reader. The `registry-scout` agent consumes the digest, opens only the entries that bear on a task, and returns them verbatim. **The index is never trimmed and generation is never delegated to judgement.** Both rules exist for the same reason: the entry an architect fails to see is exactly the entry it would have extended, and the result is a parallel implementation of something that already existed — the single failure the Data-First protocol exists to prevent. A model asked to summarise a registry can omit an entry silently; a script cannot. Measured on this repository: 779 entries indexed at roughly 17,600 tokens, against 229,000 tokens to read the four registries whole. Extend by: add a domain file and the generator picks it up with no change; add a registry and it needs one emit_group call plus its entry pattern. Never hand-edit the digest — it is regenerated, and an edit is lost at the next run while looking authoritative until then.
